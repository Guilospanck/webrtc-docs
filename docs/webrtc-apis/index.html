WebRTC APIs

Where to actually change configs when we want to remediate something that’s happening.

RTCRtpSender.setParameters()

This exists in an instance of RTCRtpSender.

💡 You CAN’T create the parameters object yourself. You MUST first call getParameters(), modify the received parameters object and then pass that object into setParameters().

Interesting points

  • There is this degradationPreferenceparameter that can be used to allow the WebRTC layer to handle the optimisation of performance in constrained-bandwidth situations.
  • maxBitrate (per encoding)
  • maxFramerate (per encoding)
  • priority(per encoding): this might be interesting for us to focus on the audio part when bandwidth is bad
  • scaleResolutionDownBy(per encoding; this is video only)

Example

One use case of setParameters() is to try to reduce network bandwidth used in constrained environments by altering the resolution and/or bit rate of the media being transmitted by the RTCRtpSender.

Example of a compatible version that will work in all browsers, even if they don’t implement them yet.

async function setVideoParams(sender, height, bitrate) {
  const scaleRatio = sender.track.getSettings().height / height;
  const params = sender.getParameters();

  // If encodings is null, create it
  params.encodings ??= [{}];
  params.encodings[0].scaleResolutionDownBy = Math.max(scaleRatio, 1);
  params.encodings[0].maxBitrate = bitrate;
  await sender.setParameters(params);

  // If the newly changed value of scaleResolutionDownBy is 1,
  // use applyConstraints() to be sure the height is constrained,
  // since scaleResolutionDownBy may not be implemented

  if (sender.getParameters().encodings[0].scaleResolutionDownBy === 1) {
    await sender.track.applyConstraints({ height });
  }
}

RTCRtpReceiver.jitterBufferTarget()

→ LIMITED BROWSER AVAILABILITY (circa Feb/26)

💡 A “high jitter” indicates that the packets are arriving at significantly varying rates, possibly due to network congestion, packet loss, and routing of packets in a stream through different paths.

💡 The jitter buffer is just a buffer that stores temporarily the incoming packets and then released them in steady, synchronised rate.
They may also do other things like apply error correction (FEC) to fix corrupted packets, re-request missing packets, use audio samples to conceal missing packets (PLC: Packet Loss Concealment) or even slow down/speed up sample playout.

The buffer is tradeoff between having a delay or having missing packets.

Note that the value should be positive and less than 4000 milliseconds.

→ Also: this only influences that jitter buffer actual size (it does NOT directly set it). The actual jitter buffer target will vary between max and minimum allowed values that reflects the networks conditions and memory constraints and can change at any time.

💡 Note: jitter is given in seconds. Jitter buffer is in milliseconds.
