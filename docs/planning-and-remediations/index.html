Planning and Remediations

When planning constraints and things like that:

  • Choose the right codec.
  • Focus on what your application actually uses.
  • Use the Pareto principle and act on the lower hanging fruits first. Things to be aware: frequency that something happens, how important it is, complexity, effort. In other words: ROI (return on investment).

Count pixels

One good way to prevent of using unneeded resources.

💡 As a rule of thumb, you should NOT send or receive more than 100M pixels per second.

Example:
Receiving 2 incoming video streams of 720p@30fps?
That amounts to 1,280_720_30*2 = 55,296,000 < 100M 👉 High
but doable number of pixels on a desktop.

➡️ Effectively managing bandwidth is half of the battle.

WebRTC APIs

Where to actually change configs when we want to remediate something that’s happening.

RTCRtpSender.setParameters()

This exists in an instance of RTCRtpSender.

💡 You CAN’T create the parameters object yourself. You MUST first call getParameters(), modify the received parameters object and then pass that object into setParameters().

Interesting points

  • There is this degradationPreferenceparameter that can be used to allow the WebRTC layer to handle the optimisation of performance in constrained-bandwidth situations.
  • maxBitrate (per encoding)
  • maxFramerate (per encoding)
  • priority(per encoding): this might be interesting for us to focus on the audio part when bandwidth is bad
  • scaleResolutionDownBy(per encoding; this is video only)

Example

One use case of setParameters() is to try to reduce network bandwidth used in constrained environments by altering the resolution and/or bit rate of the media being transmitted by the RTCRtpSender.

Example of a compatible version that will work in all browsers, even if they don’t implement them yet.

async function setVideoParams(sender, height, bitrate) {
  const scaleRatio = sender.track.getSettings().height / height;
  const params = sender.getParameters();

  // If encodings is null, create it
  params.encodings ??= [{}];
  params.encodings[0].scaleResolutionDownBy = Math.max(scaleRatio, 1);
  params.encodings[0].maxBitrate = bitrate;
  await sender.setParameters(params);

  // If the newly changed value of scaleResolutionDownBy is 1,
  // use applyConstraints() to be sure the height is constrained,
  // since scaleResolutionDownBy may not be implemented

  if (sender.getParameters().encodings[0].scaleResolutionDownBy === 1) {
    await sender.track.applyConstraints({ height });
  }
}

RTCRtpReceiver.jitterBufferTarget()

→ LIMITED BROWSER AVAILABILITY (circa Feb/26)

💡 A “high jitter” indicates that the packets are arriving at significantly varying rates, possibly due to network congestion, packet loss, and routing of packets in a stream through different paths.

💡 The jitter buffer is just a buffer that stores temporarily the incoming packets and then released them in steady, synchronised rate.
They may also do other things like apply error correction (FEC) to fix corrupted packets, re-request missing packets, use audio samples to conceal missing packets (PLC: Packet Loss Concealment) or even slow down/speed up sample playout.

The buffer is tradeoff between having a delay or having missing packets.

Note that the value should be positive and less than 4000 milliseconds.

→ Also: this only influences that jitter buffer actual size (it does NOT directly set it). The actual jitter buffer target will vary between max and minimum allowed values that reflects the networks conditions and memory constraints and can change at any time.

💡 Note: jitter is given in seconds. Jitter buffer is in milliseconds.

To think

Interesting Signal article: https://signal.org/blog/how-to-build-encrypted-group-calls/

  • Each participant says what is the maximum resolution it wants
  • Congestion control
  • Simulcast, SVC, SFU
  • Based on the metrics, inform the sender that there’s something wrong

Events to look after

Burst loss

This is not a metric by itself, but something that you should infer from deltas between polls. It’s usually due to:

  • Wi-Fi interference: weak signal, microwave, roaming between Access Points (APs)
  • Cellular handoff: 4G ↔ 5G, tower change
  • Some local router overflowing stuff
  • CPU spikes: the sender unable to encode in time
  • Network drops

Typical burst loss timeline:

Timenackretransmitbitratejitterfreeze
t01low1.2mbps8ms0
t130high1.2mbps60ms0
t245very high900kbps80ms1
t32low600kbps12ms1

That spike between t1–t2 is burst loss.

Ways to detect it:

A) nackCount spike

This is a very strong signal for a burst loss.

RTCOutboundRtpStreamStats.nackCount

# This increments when the receiver
# tells you it missed packets.

Detecting it:

nackDelta > threshold within short window

# Example:
if (nackDelta > 15) {
  // likely burst
}

B) retransmittedBytesSent spike

RTCOutboundRtpStreamStats.retransmittedBytesSent

# If there are packet being lost, this will increase

Detecting it:

retransmitBitrate = delta(retransmittedBytesSent) / deltaTime

# Example
if (retransmitBitrate > totalBitrate * 0.3) {
// burst recovery in progress
// This indicates that RTX (retransmission) is working hard
// to recover from burst loss.
}

C) fractionLost spike (remote view) - LIMITED AVAILABILITY

RTCRemoteInboundRtpStreamStats.fractionLost
# it provides a value that can be used to determine
# the fraction of packets lost for this SSRC in the last
# reporting interval.

Detecting it:

lossRate = fractionLost / 256

// if lossRate jumps from 0.01 -> 0.25 -> 0.02
// within 1-2 seconds, that's a burst

D) jitter spike

RTCInboundRtpStreamStats.jitter // seconds

# if jitter suddenly increases
# Example
# jitterMs > 40
# combined with nack spike and retransmit spike
# Then VERY LIKELY burst loss

E) Frame freezes (video)

freezeCount delta > 0

# if this increases right after nack spike, then it's 
# classic burst effect

What to do when burst loss is detected

Fast downshift. Slow upshift.

Temporary bitrate reduction

const params = sender.getParameters();

for (const enc of params.encodings ?? []) {
  if (typeof enc.maxBitrate === "number") {
    enc.maxBitrate = Math.floor(enc.maxBitrate * 0.75);
  }
}

await sender.setParameters(params);

Delay recovery

Do NOT immediately increase bitrate again. Wait for:

  • RTT stable
  • nackDelta low
  • retransmit ratio < 5%
  • stable for 5-10 seconds

Then slowly increase:

enc.maxBitrate *= 1.1

Optional: increase jitter buffer on the receiver side

// if supported (LIMITED AVAILABILITY)
receiver.jitterBufferTarget = 200; // ms

Appendix

Simple burst loss detector:

interface BurstDetectionResult {
  detected: boolean;
  severity: "mild" | "moderate" | "severe";
}

function detectBurstLoss(metrics: {
  nackDelta?: number;
  retransmitBitrateBps?: number;
  totalBitrateBps?: number;
  packetLossRate?: number;
  jitterMs?: number;
}): BurstDetectionResult {

  const {
    nackDelta = 0,
    retransmitBitrateBps = 0,
    totalBitrateBps = 1,
    packetLossRate = 0,
    jitterMs = 0,
  } = metrics;

  const retransmitRatio = retransmitBitrateBps / totalBitrateBps;

  // Strong burst indicators
  const severe =
    nackDelta > 25 ||
    retransmitRatio > 0.5 ||
    packetLossRate > 0.2;

  const moderate =
    nackDelta > 10 ||
    retransmitRatio > 0.3 ||
    packetLossRate > 0.1 ||
    jitterMs > 40;

  if (severe) return { detected: true, severity: "severe" };
  if (moderate) return { detected: true, severity: "moderate" };

  return { detected: false, severity: "mild" };
}

Uplink Congestion

When the sender is transmitting more media data than the network path can sustain.

💡 The key difference between uplink congestion and burst loss is that:
Congestion is gradual and persistent.

Burst loss is sudden and short.

Meaning:

  • Your outbound bitrate > available uplink capacity
  • Packets get delayed or dropped
  • RTT increases
  • Loss increases
  • Congestion controller reacts (reduces bitrate)

It has a pattern over time. It usually looks like:

  • RTT gradually increasing
  • remote-inbound-rtp.fractionLost rising
  • retransmittedBytesSent increasing (due to packet loss)
  • availableOutgoingBitrate (the network uplink capacity - kinda) decreasing
  • Eventually bitrate drops (congestion controller kicks in)

Uplink congestion timeline:

TimeRTTLossBitrateAvailable
t080ms1%1.5Mbps2.0Mbps
t1120ms3%1.6Mbps1.4Mbps
t2220ms8%1.7Mbps900kbps
t3450ms12%1.7Mbps600kbps
t4350ms4%600kbps700kbps

Notice:

  • RTT increases before collapse
  • Available bitrate (network uplink capacity - of some sorts) drops
  • Loss increases
  • Then the congestion controller slams bitrate down

Ways to detect it

A) RTT increasing

RTCRemoteInboundRtpStreamStats.roundTripTime
# or the fallback
RTCIceCandidatePairStats.currentRoundTripTime

# convert to ms
rttMs = roundTripTime * 1000

If it is steadily increasing, and it’s sustained, possibly uplink congestion.

B) Remote loss rising (LIMITED AVAILABILITY)

RTCRemoteInboundRtpStreamStats.fractionLost
# it provides a value that can be used to determine
# the fraction of packets lost for this SSRC in the last
# reporting interval.

Detecting it:

lossRate = fractionLost / 256

// if sustained > 5-10% AND
// combined with RTT rise
// => Classic uplink congestion

C) retransmittedBytesSent increasing

RTCOutboundRtpStreamStats.retransmittedBytesSent

# If there are packet being lost, this will increase

Detecting it:

retransmitBitrate = delta(retransmittedBytesSent) / deltaTime
retransmitRatio = retransmitBitrate / totalBitrate

# Example
if > 20-30% sustained => recovery overload

D) availableOutgoingBitrate dropping (LIMITED AVAILABILITY)

RTCIceCandidatePairStats.availableOutgoingBitrate

E) Bitrate collapses after spike

Congestion controllers (GCC) react by sharply reducing bitrate

If you see a drop in the bitrate after RTT/loss increase ⇒ congestion confirmed.

How to mitigate

💡 Important: do NOT trigger on a single sample. Use time windows. For example:

  • 3-5 consecutive samples

  • 5-15 second window

💡 You could also proactively downshift before loss happens, for example by checking the
totalBitrate > availableOutgoingBitrate

Fast downshift. Slow upshift. (same as burst loss).

Cap maxBitrate

async function reduceBitrate(sender: RTCRtpSender) {
  const p = sender.getParameters();

  for (const e of p.encodings ?? []) {
    if (typeof e.maxBitrate === "number") {
      e.maxBitrate = Math.floor(e.maxBitrate * 0.7);
    }
  }

  await sender.setParameters(p);
}

Reduce resolution

e.scaleResolutionDownBy *= 1.2;
// This works by reducing the encoder load and bitrate demand.

Reduce framerate

e.maxFramerate = 15;
// very effective for screen share

Slow recovery ramp

Do it slowly after stabilization

e.maxBitrate *= 1.05; // very slow increase

Production-grade uplink strategy

  1. Detect sustained congestion
  2. Immediate 30% bitrate reduction
  3. Disable highest layer if still unstable
  4. Wait 8-15s stable before ramp
  5. Ramp up slowly (5% per window)

Appendix

Detection logic. We look for:

  • Sustained RTT increase
  • Sustained loss
  • Sustained retransmit ratio
  • Outgoing bitrate > available capacity
interface UplinkSignals {
  rttMs?: number;
  packetLossRate?: number; // 0..1
  retransmitBitrateBps?: number;
  totalBitrateBps?: number;
  availableOutgoingBitrate?: number;
}

export function detectUplinkCongestion(s: UplinkSignals): boolean {
  const rttHigh = (s.rttMs ?? 0) > 300;
  const lossHigh = (s.packetLossRate ?? 0) > 0.08;

  const retransmitRatio =
    s.totalBitrateBps && s.retransmitBitrateBps
      ? s.retransmitBitrateBps / s.totalBitrateBps
      : 0;

  const highRecoveryLoad = retransmitRatio > 0.25;

  const overshooting =
    s.availableOutgoingBitrate &&
    s.totalBitrateBps &&
    s.totalBitrateBps > s.availableOutgoingBitrate * 1.2;

  return (
    (rttHigh && lossHigh) ||
    (highRecoveryLoad && rttHigh) ||
    overshooting
  );
}

Downlink congestion

💡 The network path delivering media TO YOU cannot sustain the incoming bitrate.
It’s about what you’re RECEIVING. You are not being able to receive everything.

It means:

  • Remote sender is transmitting too much
  • Your download path can’t keep up
  • Packets are delayed or dropped
  • Jitter buffer grows
  • Frames are dropped
  • Video freezes

Downlink congestion timeline:

TimeLossJitterFreezeBitrate
t01%8ms01.5Mbps
t14%25ms01.5Mbps
t29%60ms11.2Mbps
t38%55ms2900kbps
t47%40ms3700kbps

Notice:

  • Jitter raises
  • Loss sustained
  • Freeze increments repeatedly
  • Bitrate eventually drops (remote react with congestion controller)

Ways to detect it

💡 Use a 2-3 consecutive windows before triggering.

A) Inbound packet loss

RTCInboundRtpStreamStats.packetsLost
RTCInboundRtpStreamStats.packetsReceived

lossRate = lostDelta / (lostDelta + receivedDelta)

If sustained:

  • More than 5% video
  • More than 3% audio

Congestion likely.

B) Jitter spike

RTCInboundRtpStreamStats.jitter // seconds

jitterMs = jitter * 1000

If sustained > 30-50ms ⇒ unstable path.

C) Jitter buffer growth

💡 - jitterBufferDelay: accumulated time that all audio samples and complete video frames have spent in the jitter buffer.

  • jitterBufferEmittedCount: indicates the total number of audio samples and/or video frames that have come out of the jitter buffer.

Both of them are incremented when samples or frames exit the buffer. The average jitter buffer delay is jitterBufferDelay / jitterBufferEmittedCount

If growing buffer ⇒ network instability.

D) Freeze count

RTCInboundRtpStreamStats.freezeCount

If increasing, visible congestion impact.

E) Incoming bitrate decreasing unexpectedly

RTCInboundRtpStreamStats.bytesReceived

If the bitrate suddenly drops without you changing the sender ⇒ remote is reacting to congestion.

How to mitigate

You don’t actually control this. You’re only the receiver. What you can do is signalise to the sender that you’re experiencing bad connection.

One example would be to use the signalling channel:

.emit("network-warning", {
  type: "downlink-congestion",
  severity: "moderate"
});

If supported, you could also increase jitter buffer, although it is not always supported (LIMITED AVAILABILITY) and you’re gonna tradeoff for increased latency.

RTCRtpReceiver.jitterBufferTarget = 200; // ms

// Increases latency
// Reduces freezes
// Better for screen share

Production-ready strategy

  1. Detect sustained inbound loss + jitter
  2. If SFU: switch to lower layer
  3. If P2P: signal remote to reduce bitrate
  4. Increase jitter buffer slightly if needed

Distinguishing Downlink from Device Overload

If:

  • Loss high
  • Jitter high
  • RTT stable (maybe: may rise, may stay moderate)
  • CPU normal

Then it’s a network downlink congestion.

If:

  • No packet loss
  • FreezeCount rising
  • FramesDropped high (in the Web you can get it from https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/getVideoPlaybackQuality)
  • CPU high

Then it’s decoder/render overload (not congestion).

Appendix

Detecting downlink congestion.

We combine:

  • Sustained inbound loss
  • Sustained jitter
  • Increasing freezeCount
  • Degrading bitrate
interface DownlinkSignals {
  packetLossRate?: number;
  jitterMs?: number;
  freezeDelta?: number;
  inboundBitrateBps?: number;
}

export function detectDownlinkCongestion(s: DownlinkSignals): boolean {
  const lossHigh = (s.packetLossRate ?? 0) > 0.07;
  const jitterHigh = (s.jitterMs ?? 0) > 40;
  const freezing = (s.freezeDelta ?? 0) > 0;

  return (
    (lossHigh && jitterHigh) ||
    (lossHigh && freezing)
  );
}

Encoder overload

💡 Your CPU/GPU cannot encode video frames fast enough in real time.

This is a media pipeline bottleneck on the sender side.

The main difference to the network congestion is that network signals stay clean.

💡 Quick mental model:

  • Encoder overload: CPU can’t keep up

  • Congestion: network can’t keep up

Encoder overload timeline:

TimeFPSEncodeTimeRTTLoss
t03018ms80ms0%
t12228ms85ms0%
t21445ms82ms0%
t31060ms78ms0%

Notice that:

  • RTT stable
  • Loss zero
  • FPS collapsing
  • Encode time increasing

Common causes

  1. Screen sharing at high resolution
  2. 4K webcam capture
  3. Software encoder instead of hardware
  4. CPU spike from background processes
  5. Running inside VM
  6. Thermal throttling
  7. Too many simulcast layers
  8. Encoding AV1 on weak CPU

Ways to detect it

Look at outbound stats (RTCOutboundRtpStreamStats):

  • framesEncoded
  • framesPerSecond
  • totalEncodeTime
  • totalPacketSendDelay

A) FPS drops unexpectedly

fps = delta(framesEncoded) / deltaTime

B) Encode time per frame is high

avgEncodeTime = totalEncodeTime / framesEncoded

// If

avgEncodeTime > 1 / targetFPS

Example:

  • 30 FPS target ⇒ 33ms per frame budget
  • If encode time = 45ms per frame ⇒ encoded cannot sustain 30 FPS

This is a strong encoder overload signal.

C) Bitrate looks fine but video looks bad

If:

  • Bitrate looks fine
  • RTT looks normal
  • Packet loss looks good (= 0)
  • But FPS is low

Then encoder bottleneck.

D) No retransmission spike

Congestion shows retransmittedBytesSent ⬆️. Encoder overload does not.

How to mitigate

You do media-side adjustments, not network ones.

A) Reduce resolution

Most effective fix.

enc.scaleResolutionDownBy *= 1.5

B) Reduce framerate

Huge relief for the CPU.

enc.maxFramerate = 15

C) Reduce simulcast layers

Disable highest layer.

D) Prefer hardware-friendly codec

Example, prefer H264 over VP9 on some devices.

Appendix

Detection logic.

The key rule is:

low FPS + high encode time + clean network = encoder overload
interface EncoderSignals {
  fps?: number
  avgEncodeTimeMs?: number
  rttMs?: number
  packetLossRate?: number
}

function detectEncoderOverload(s: EncoderSignals) {
  const lowFps = (s.fps ?? 30) < 15
  const encodeSlow = (s.avgEncodeTimeMs ?? 0) > 40
  const networkClean =
    (s.packetLossRate ?? 0) < 0.02 &&
    (s.rttMs ?? 0) < 200

  return lowFps && encodeSlow && networkClean
}

Receiver overload

💡 The receiving device cannot decode or render incoming video fast enough.

It’s a CPU/GPU bottleneck on the receiving side.

Receiver overload timeline:

TimeFPSLossRTTJitterFreeze
t0300%80ms8ms0
t1220%75ms7ms0
t2140%78ms9ms1
t3100%80ms8ms2

Notice:

  • Loss stable
  • RTT stable
  • Jitter stable
  • FPS collapsing
  • Freeze count increasing

Common causes

  1. Weak laptop CPU
  2. Mobile device thermal throttling
  3. 1080p or 4K video on weak device
  4. Too many simultaneous video streams
  5. AV1 decoding on unsupported hardware
  6. Software decoded instead of hardware decode
  7. Browser tab in background
  8. GPU under heavy load

Ways to detect it

Look at RTCInboundRtpStreamStats:

  • framesDecoded (limited availability)
  • freezeCount (if available)
  • totalProcessingDelay
  • jitter
  • packetsLost
  • bytesReceived

And optionally from the video element:

// HTML5 video element
video.getVideoPlaybackQuality()

A) FreezeCount increasing

freezeDelta = currentFreeze - previousFreeze

If this increases while:

  • packet loss low
  • RTT normal
  • Jitter low

Likely to be receiver overload.

B) FPS dropping

C) High processing delay

RTCInboundRtpStreamStats.totalProcessingDelay

# compute

avgProcessingDelay = totalProcessingDelay / framesDecoded

If decode/render delay per frame is high ⇒ overload.

D) Video element dropped frames

video.getVideoPlaybackQuality().droppedVideoFrames

If:

  • droppedVideoFrames increasing
  • and packet lost stable 0

Then it’s rendering overload.

How to mitigate

Unlike uplink congestion and encoder overload, you cannot adjust locally. You must, if possible, reduce what you’re receiving (SFU, simulcast) or signal the sender.

A) Switch to lower simulcast layer

B) Ask remote sender to reduce bitrate (P2P case)

The remote sender can reduce:

  • Bitrate
  • Framerate
  • Resolution

C) Limit decode complexity

  • Prefer H264 over AV1 on weak devices
  • Avoid too many active video tracks

Appendix

Detection logic.

The key rule is:

playback bad + network clean = receiver overload
interface ReceiverSignals {
  fps?: number
  freezeDelta?: number
  packetLossRate?: number
  jitterMs?: number
  rttMs?: number
}

function detectReceiverOverload(s: ReceiverSignals) {
  const lowFps = (s.fps ?? 30) < 15
  const freezing = (s.freezeDelta ?? 0) > 0
  const networkClean =
    (s.packetLossRate ?? 0) < 0.02 &&
    (s.jitterMs ?? 0) < 20 &&
    (s.rttMs ?? 0) < 200

  return (lowFps || freezing) && networkClean
}
